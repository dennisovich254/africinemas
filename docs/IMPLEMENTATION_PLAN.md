> **Architecture reference:** `docs/architecture.md` ("§n" below means a section of that document)
> **Stack:** Jac 0.37.x (pinned), one shared deployment, Postgres (Jac graph store), Gemini via `by llm`, M-Pesa Daraja (sandbox)

## 1. Context

AfriCinemas is a multi-tenant cinema SaaS. A cinema owner signs up, configures venues, screens, seat layouts, movies and screenings, and gets a public storefront. Customers pick seats and pay with M-Pesa, then receive QR tickets that ushers scan at the door. Owners see revenue and occupancy, and AI features help both owners and customers.

The product ships as **one Jac workspace with three clients over one server**:

| Client | Jac kind | UI tech | Purpose |
| --- | --- | --- | --- |
| `web` | `web-app` | React DOM (jac-shadcn) | The server, the public storefront, and the full owner/staff back-office |
| `desktop` | `desktop` | Same React DOM bundle in an OS webview | Counter / box office / admin station. `backend = <server URL>`, so there is **no embedded DB** |
| `mobile` | `mobile` | Native React Native screens (`@jac/mobui`) | Customer booking and tickets, usher QR scanner (camera), box-office quick sale, owner summary |

Desktop reuses the web UI unchanged. Mobile needs its own screens (mobUI rejects HTML), but **all business logic and API wrappers live in shared modules**, so the mobile app is a thin view layer.

### 1.1 Responsive web: phone and PC are both first-class

Most customers will book on a phone, in a mobile browser, without installing the app. So the **web app itself must be fully usable at phone width**. The native mobile app is an extra, not the only mobile experience.

| Surface | Primary device | Approach |
| --- | --- | --- |
| Public storefront (browse, seat map, checkout, tickets) | **Phone** | **Mobile-first.** Designed at 375 px first, then enhanced for tablet/PC. Sticky bottom action bar (selected seats, total, "Pay with M-Pesa"). Tap targets ≥ 44 px. Pinch/zoom + pan on the seat map. Single-column checkout. Tickets readable offline once loaded. |
| Staff tools (scanner, box-office sale) | Phone / tablet | Mobile-first, one-hand use, large buttons. |
| Back-office (dashboard, movies, screenings, staff, settings) | **PC** | Desktop-first, but **fully responsive**: the sidebar collapses to a drawer and wide tables become cards. Owners can check the dashboard and approve things on a phone. |
| Seat layout designer | PC | Needs a wide screen. Below 768 px it shows a read-only preview with a clear "Use a larger screen to edit layouts" message, not a broken editor. |

Breakpoints (Tailwind defaults, used everywhere): **base = phone (≥ 360 px)**, `sm` 640, `md` 768 (tablet), `lg` 1024 (laptop), `xl` 1280 (desktop). No horizontal page scroll at any width, and no hover-only interactions.

Optional (decided at 4.6: deferred to Phase 6, with tickets): `[client.pwa]` makes the storefront installable from the browser, with an offline ticket view.

## 2. How we work (applies to every sub-phase)

### 2.1 The TDD loop — "one sub-phase = one PR"

```text
1. Branch      git switch -c feat/p<phase>.<sub>-<slug>        (e.g. feat/p4.3-seat-holds)
2. RED         Write the sub-phase's tests (listed in this plan). Run `jac test` → they FAIL for the right reason.
               Commit: "test(p4.3): seat hold concurrency and expiry"
3. GREEN       Implement the minimum to pass. `jac test` → all green (new + all previous).
4. REFACTOR    Clean up with tests green. Validate every new .jac via the jac MCP (validate_jac) / `jac check`.
5. GATE        Local: pre-commit + pre-push hooks pass. Remote: every required CI check passes.
6. MERGE       Squash-merge the PR into main. Tick the box in this file. Only then start the next sub-phase.
```

**Definition of Done (per sub-phase):**
- [ ] Every test in the sub-phase's "Tests" list exists and passes, and no earlier test regressed.
- [ ] `jac fmt --check .`, `jac check --lint .` and `jac check` are clean.
- [ ] New endpoints are registered in the **tenant-isolation registry** (§2.3) and have cross-tenant tests.
- [ ] Any new external side effect goes through `on_commit` or the outbox, with a replay test (§25/§29 of the architecture doc).
- [ ] UI sub-phases: the Playwright E2E happy path passes. Mobile: the device checklist is ticked.
- [ ] UI sub-phases: follow `design-system/africinemas/MASTER.md` (plus any page override). Run the **ui-ux-pro-max** skill's pre-delivery checklist (`references/pro-rules.md` for mobile). Screenshots at 375 / 768 / 1440 px attached to the PR.
- [ ] UI sub-phases: the E2E happy path passes on **both** the `mobile` (Pixel 7, 412 px, touch) and `desktop` (1440 px) Playwright projects. An automated check asserts **no horizontal overflow** and **tap targets ≥ 44 px** at 375 px.
- [ ] Docs updated: this file's checkbox, plus an ADR if a decision was made.

### 2.2 Test pyramid and where tests live

| Layer | Tool | Location | Runs in |
| --- | --- | --- | --- |
| Unit (pure logic: pricing, state machines, validators, QR signing) | `test` blocks / `.test.jac` annexes | beside the module in `core/` | pre-push, CI |
| API / integration (endpoints, auth, graph effects, multi-user) | `JacTestClient` with a fresh `tempfile.mkdtemp()` base_path per test | `tests/api/` | pre-push, CI |
| Concurrency (races: holds, redemption, callbacks, idempotency) | real `jac run` server + parallel HTTP (`flow`/`wait`) | `tests/concurrency/` | CI |
| Tenant isolation (A → B on every endpoint) | shared two-tenant fixture + endpoint registry | `tests/isolation/` | CI |
| AI | `MockLLM` (no network, no key) | `tests/ai/` | CI |
| Web E2E | Playwright (`@playwright/test`) against `jac run`, with two projects: `mobile` (Pixel 7 emulation, touch) and `desktop` (1440×900). Every spec runs in both | `e2e/` | CI |
| Load | Python load script (`tests/load/`) | manual + pre-release |
| Mobile | shared-logic unit tests + `jac check --app mobile` + web build; device checklist | `mobile/` | CI (+ manual) |

Rules (from the Jac testing guide): never name files `test_*.jac`. Each test builds its own data (tests run in parallel workers and must not depend on each other). Never call a real LLM or Daraja in CI.

### 2.3 Tenant-isolation registry

`tests/isolation/registry.jac` lists every endpoint with its scope and an A→B probe. A **meta-test** compares it against the endpoints the app really serves (its `/openapi.json` routes; `jac run --faux` headings are unreliable, JI-004). An endpoint missing from the registry fails CI, so no new endpoint can skip the isolation tests.

### 2.4 Conventions

- **Commits:** Conventional Commits (`feat|fix|test|refactor|docs|chore|ci(scope): …`), enforced by a commit-msg hook and a PR-title check.
- **Branches:** `feat/…`, `fix/…`, `chore/…`, `docs/…`. No direct commits to `main`.
- **Decisions:** Architecture Decision Records (ADRs) in `docs/adr/NNNN-title.md`.
- **Secrets:** `.env` (gitignored) locally, GitHub Actions secrets in CI, never in `jac.toml` (use `${VAR}` interpolation).

### Phase 12 — Snacks: a product catalog, variants, add-ons, combos and inventory, then selling them

Rebuilt (2026-10-11) from the user's design guide, "Designing the Snack Management System for a Multitenant Cinema Platform". The first attempt (simple items with shared option lists) is kept on the local branch `archive/p12.1-first-try`, not merged.

**Model (from the guide):**
- **Category:** how products are organized for staff and customers (Popcorn, Beverages, Crisps & Chips, Candy & Chocolates, Hot Food, Combos & Deals). Editable, ordered, shallow (a category and at most one subcategory level later). Never used for size, flavour or brand.
- **Product:** a tenant-owned product family (Popcorn, Coca-Cola, Doritos Nacho Cheese), with a category, an optional brand, a description, tags, images and a type: *single*, *with variants* or *combo*. Lifecycle: **draft → active → archived** (archived stays for reporting, can't be bought; a product referenced by an order is archived, never deleted).
- **Variant:** what the customer actually buys (Small, Medium, Large; 300 ml, 500 ml, 1 litre). Each has a **persistent id**, its option values (up to 2 option axes such as Size and Flavour, without forcing every combination), a SKU unique in the cinema, an optional barcode, its price, whether it's available, and whether its stock is tracked. A single product has one variant.
- **Add-on group (modifier):** optional or required extras on a product (Extra toppings: butter +30, caramel +50), with min/max selections, per-option price and availability. Sizes are variants, never add-ons.
- **Combo:** a product of type combo with its own price and components: a fixed variant ("1 × Large Popcorn") or a choice among eligible variants ("2 drinks from Beverages"). A combo can't be sold when a component it needs is out.
- **Locations** are the cinema's venues: a product and each variant can be on or off per venue, with an optional per-venue price that overrides the variant's price.
- **Inventory** (finished items first; recipes later): per variant per venue, `on_hand`, `reserved` and `available = on_hand − reserved`, a low-stock threshold, and what happens at zero (mark unavailable, or allow sales for prepared snacks). Every change is a **movement** with a reason (received, damaged, count correction, sale, release, other), quantity, user and time; stock is never overwritten.
- **Multitenancy:** everything belongs to one cinema (tenant), checked on the server for every id (ADR-0004, ADR-0008); SKUs are unique per cinema (atomic claims, ADR-0007); stock changes are single atomic statements, so two customers can't buy the last bottle.
- **Roles (existing, user decision 2026-10-10):** the owner, tenant admin and general manager manage the catalog, prices and inventory; the box office manager and agent mark availability, record stock adjustments at their venues and run the snack counter. Customers collect snacks at the counter (decision 2026-10-10).

### Phase 14 — Trust: only verified cinemas reach the public

Planned 2026-10-22 from improvements #18 ("verify the owner and the business") and the threat model (`docs/security/threat-model.md` §1, "Fraudulent and impersonating cinemas"). **Model:**
- **Cinema states** (existing, `core/tenancy/state.jac`): `configuring` → `ready_for_go_live` → `active` ↔ `suspended`. Only **`active`** is public. `ready_for_go_live` means "submitted for review".

### Phase 15 — Each cinema's own M-Pesa, and the AfriCinemas fee

Planned 2026-10-22. **The business model:** AfriCinemas charges each cinema a fee on every booking made through the platform. Decisions (owner, 2026-10-22):
- **Money flow B:** each cinema takes its customers' money into its **own** M-Pesa paybill or till (improvements #15), and AfriCinemas **invoices the cinema** for its fees each month. AfriCinemas never holds customers' money. (Collecting everything and paying cinemas out would very likely be payment-service activity needing Central Bank of Kenya authorisation under the National Payment System Act; splitting at source through a licensed provider stays an option for later.) Until a cinema's own paybill is connected, payments keep using the platform's paybill, for the demo only.
- **The cinema pays, not the customer:** customers see no AfriCinemas fee. A cinema's own booking fee in its price list stays the cinema's.
- **The rates** (owner, 2026-10-26, "model C", replacing 10% of everything): **online** (storefront, Claude), **7%** on tickets, 3D glasses and the cinema's booking fee, and **20%** on snacks; **at the box office**, cash or M-Pesa, **3%** on everything. Our pitch is selling more snacks, so that's where we earn most; tickets stay low because distributors take about half of each one. Glasses are a snack product in the catalogue (P12.13), but they're charged at the ticket rate.
- **The fee on refunds** (owner, 2026-10-26, replacing "the fee isn't refunded"): an **M-Pesa refund** credits the fee on what's refunded, since the money's return can be checked; a **cash refund** keeps the fee, since it can't be checked and would otherwise let a cinema sell for cash, mark it refunded and pay nothing (cinemas can refund cash sales by M-Pesa instead); a refund caused by a **Platform failure** always credits the fee.

**Principles:** every paid order is the record, and what a cinema owes is calculated from those records, never kept as a running total. Fees are frozen on the order when it's paid, with the rule that set them, so changing the fee never changes past orders. Ledger entries are only added, never edited. Everything is shown to the cinema as plainly as it's shown to us.

**Legal checkpoints** (confirm with a Kenyan lawyer and accountant before production): the fee is in the agreement every cinema accepts; 16% VAT on the fee once AfriCinemas is VAT-registered (required above KES 5 million turnover a year); invoices through KRA's eTIMS; a cinema's own paybill is in the cinema's name (Phase 14's verified business).

**AfriCinemas' own legal footing** (owner, 2026-10-24: everything Kenyan law requires to run this as a business; looked up 2026-10-24, to be confirmed by a Kenyan advocate and accountant, since the rules below come partly from secondary sources and some were changing):
- **Who is who.** AfriCinemas runs the platform and is the cinemas' ticketing agent; each cinema is the seller of its tickets and snacks, takes the money into its own M-Pesa (money flow B) and answers for its shows. Every page and document says so.
- **Data protection (Data Protection Act, 2019).** AfriCinemas is the **controller** of its own accounts (owners, staff, platform staff) and verification data, and the **processor** for each cinema's customer data. So: registration with the Office of the Data Protection Commissioner (exempt below KES 5 million turnover *and* under 10 employees, unless in a listed sector; certificate renewed every 24 months), a written **data processing agreement** with every cinema, a **data protection impact assessment** for the ID photos and documents, a breach procedure (the Commissioner told within 72 hours), and a way to answer people's requests to see, correct or delete their data.
- **Tax (KRA).** AfriCinemas' own PIN and business registration; **VAT** at 16% on the fee once registered (required above KES 5 million turnover a year); every fee invoice an **eTIMS** invoice, since expenses without one are disallowed for the cinema (15.4); income tax on the fees.
- **Payments (National Payment System Act, 2011).** Money flow B keeps AfriCinemas from holding customers' money, which would otherwise very likely need Central Bank authorisation as a payment service provider; the advocate confirms that, and watches the draft National Payment System Bill, 2026.
- **Consumers (Consumer Protection Act, 2012).** Clear prices before paying, who the seller is, how to complain, refunds as each cinema's policy says (14.3b, 14.3c).
- **Cinemas' own licences** (Films and Stage Plays Act: the KFCB film exhibition licence; the county business permit) stay the cinema's, checked at verification (14.4).

Payments then go straight to the cinema's paybill. — **T:** keys are never returned by any endpoint after saving; an unverified cinema is refused; a name mismatch is refused; a change waits and notifies; each cinema's payments use its own keys (the simulator records which); isolation: no cinema reaches another's keys; e2e: connect, test payment, switch. **Built (ADR-0082):** owner decision (2026-10-28): cinemas' own paybills with AfriCinemas' fees billed monthly (15.4, 15.5), not split at payment through a gateway; AfriCinemas never holds a cinema's money. The keys are sealed with AES-256-GCM (`AFRICINEMAS_MPESA_KEY`, bound to the cinema, version and field); every connection is a new version, and each payment is sent and checked with the version it was made with; a change waits 24 hours from when it was asked for, every owner is emailed, and it can be cancelled until then; against live Daraja a cinema without its own account can't take M-Pesa. The name check is against what the owner declares (Daraja can't look a paybill's name up); the test payment's prompt shows the real name.
- [x] **15.4 Monthly statements and invoices** — on the 1st of each month, each cinema gets a **statement** for the month before (bookings, gross takings by channel, refunds, AfriCinemas fees, VAT on the fees when registered, the amount due), built from 15.2's entries, and an **invoice** with a number, due date and how to pay (AfriCinemas' paybill with the invoice number as the account). Cinemas see their statements and invoices on a **Billing** page in the back office, as PDFs too; the platform console sees every cinema's. eTIMS submission when AfriCinemas registers. — **T:** a statement's totals match its orders exactly; a statement never changes once issued (a correction is a credit note); invoice numbers are sequential and never reused; a cinema sees only its own; e2e: a month of fixture orders gives the expected invoice. **Built (ADR-0083):** one statement-and-invoice per cinema per month (`core/billing/`), built from the same ledger and fee entries as Reports for the month's local days and stored once; due 5 days after issue (owner, 2026-10-28); numbers AC000001 onwards, each a permanent claim; credits carry forward; VAT at 16% once ticked on the registrations checklist; PDFs from a small built-in writer; the back office's Billing page (`financial_reports.read`) and the console's (every cinema's, and Issue what's due now). AfriCinemas' paybill is a placeholder (`AFRICINEMAS_BILLING_PAYBILL`) until it's live. Not done: credit notes, and eTIMS until AfriCinemas registers.
- [x] **15.5 Collecting what's owed** — invoices are **due**, **paid** or **overdue**. A payment to AfriCinemas' paybill with the invoice number as the account is matched to its invoice automatically (through the same M-Pesa confirmation as bookings); one that can't be matched goes to a list to match by hand. Reminders before the due date and after it; an overdue invoice shows a banner in the cinema's back office; after a grace period, a super admin may **suspend** the cinema, never automatically: its storefront goes down ("This cinema isn't available right now"), new orders and payments stop, the cinema's back office says why, and **Reinstate** undoes it; suspending and reinstating are in the platform audit log and emailed to the owner. — **T:** a matching payment marks the invoice paid once (duplicate callbacks too); a wrong account number goes to the unmatched list; reminders go on schedule; overdue shows the banner; suspension needs a person. **Built (ADR-0084):** owner decisions (2026-10-28): paid in full, the amount filled in and not editable; disputes; reminders 2 days before, on the day, 3 and 7 days after; 5 days' grace before suspension. Pay now sends an M-Pesa prompt for the invoice's amount (whole shillings) from the Billing page, settled as bookings are; a payment that can't apply goes to the console's list to match by hand or record as refunded; a dispute opens a Help request and pauses reminders and suspension until a super admin decides it stands or is waived; staff with `platform.suspend` suspend a cinema more than 5 days overdue and not disputed (its storefront says it isn't available, nothing can be sold, its back office says why) and Reinstate undoes it. Not done: payments typed in by hand at the paybill (C2B), until AfriCinemas' paybill is live.
- [x] **15.6 Reconciliation and the platform's takings** — every day, for every cinema, our ledger is checked against M-Pesa's own records (Daraja's transaction status for each payment on the cinema's paybill) and the box office's recorded cash: a payment with no order, an order with no payment, an amount that differs or a receipt used twice goes to an **exceptions list** for the cinema and the platform console. The platform overview (13.4) gains AfriCinemas' takings: fees earned, invoiced, paid and overdue, per month and per cinema. — **T:** each kind of mismatch in fixtures reaches the exceptions list, and matching records don't; the platform's takings equal the sum of the invoices; a cinema's exceptions are visible to that cinema only. **Built (ADR-0085):** owner decisions (2026-10-28): no extra Daraja credentials, so instead of Transaction Status the daily job asks M-Pesa again (the STK status query, with each payment's own account) about each payment of the last 3 days, once; and a cash-up on the Box office page compares each member's count with the cash they recorded since their last. Exceptions are kept once, resolved with a note on the back office's Reconciliation page, and listed in the console; AfriCinemas' takings (fees earned, invoiced, paid, overdue, per month and cinema) are on the console's overview. **Revised (2026-10-29):** statement uploads removed; the Reconciliation page has M-Pesa, Cash and Resolved tabs, says what each amount is instead of "ours/theirs", shows times in the cinema's time zone, and its sidebar link counts what's open. **P15.6b (ADR-0086):** no signing out with cash uncounted; a count is checked in words first and can be corrected once within 10 minutes; each cinema sets its shift length (8 h) and the largest count (KES 500,000) on Settings → Box office; cash left by someone who didn't sign out is counted on their behalf by the next agent at that venue (required before a cash sale once their shift is over, when the manager also sees "Cash not counted").

### Phase 16 — Operations: monitoring, alerts and backups (before going live)

Planned 2026-10-23. Phase 13's health signals (13.5c, ADR-0063) say what's going wrong **for one cinema**, when someone looks. Going live needs the platform's own health too: knowing **at once**, without anyone looking, when something breaks for everyone. **Owner decision (2026-10-23):** the health signals are enough while there are only demo cinemas; this phase is done before real cinemas and money arrive, and nothing in it is built earlier. Mostly existing services and Jac's own tools (`/healthz`, `/admin/ops/health`, its metrics, logs and traces), not a system of our own.

**Applies to every sub-phase:** as Phase 13. No alert ever carries a customer's details.

- [ ] **16.1 Uptime checks and alerts** — an outside service (UptimeRobot, Better Stack or similar) checks `/healthz` and the three sites (`scripts/check_sites.sh`'s addresses) every minute, and the certificate's expiry, and alerts the team by SMS and email when one stops answering. — **T:** a stopped server alerts within two minutes; the alert names the address that failed.
- [x] **16.2 Job check-ins** — every background job (ticket and support emails, the payment resolver, the hold sweeper) records when it last ran; the console's overview shows "all jobs running" or which isn't, and a job silent for three of its intervals alerts the team. — **T:** a stopped job shows on the overview and alerts; one that runs again clears it. **Built (2026-10-30):** each of the 17 jobs calls `ran()` first thing (`core/platform/jobs.jac`); a job is silent after three of its intervals and at least 5 minutes; the console overview shows "All background jobs are running" or which stopped; `check_jobs` (every 5 minutes) emails AFRICINEMAS_ALERT_EMAILS (or the super admins) once when one stops and once when it runs again; a unit test fails if a job is added without checking in.
- [x] **16.3 M-Pesa across the platform** — when failures jump across many cinemas at once, the overview says it's likely M-Pesa (Safaricom), not the cinemas, and alerts the team; Safaricom's own status is linked. — **T:** failures at one cinema don't raise it; at most cinemas within the hour, they do. **Built (2026-10-30), for any number of cinemas (owner: there won't be three soon):** `core/platform/mpesa_watch.jac`. (1) Every 5 minutes the server asks Daraja for a token with AfriCinemas' own M-Pesa app; two checks in a row without an answer means Daraja is down, with no payments needed; our own keys refused is a separate alert. (2) Real payments' failures are sorted by cause: customers' (cancelled, wrong PIN, too little money, phone off) and a cinema's keys refused (now its own health signal) are ignored; no answer, Daraja unreachable, Safaricom's own errors count, and 3 of them in 15 minutes, at least half the attempts, means M-Pesa is likely down. The console overview shows a banner with Safaricom's channels (no public status page: X and the Daraja portal); the team is emailed when it starts and ends. Counts only.
- [ ] **16.4 Error tracking** — server errors and errors in visitors' browsers (the storefront, the back office, the console) are collected by an error tracker (Sentry or similar), grouped and alerted on; this closes 13.5c's storefront errors, which then show on the cinema's health. Nothing personal is sent: no names, phones, emails or tokens. — **T:** an error in a storefront page reaches the tracker without the visitor's details; the cinema's health counts it.
- [x] **16.5 Backups and restoring them** (threat model 10.4) — the database and the media folders backed up daily, kept for an agreed time, copied off the server, and a **restore rehearsed** into a scratch server, written up as a runbook. — **T:** a restore from last night's backup brings back a cinema, its bookings and its posters; the runbook is followed by someone who didn't write it. **Built (2026-10-30):** `scripts/backup.sh` (the database with `pg_dump` and the media folder, one file encrypted with gpg to the team's backup key, whose private half is never on the server, copied off with rclone to `AFRICINEMAS_BACKUP_REMOTE`, kept **35 days** (owner) here and there, and checked in as the job "The nightly backup", silent after 36 hours); `scripts/restore.sh` (only into an empty database and media folder; checks the checksums, then that the cinemas, movies, showtimes, orders, tickets and media files match what the backup recorded); `docs/runbooks/backups.md` (set-up, restoring, after a disaster, the secrets kept apart, and a quarterly rehearsal log). Rehearsed into a scratch Postgres from a development database. The privacy policy states the 35 days. **Left:** the off-the-server storage is chosen with hosting (P17.3), and the first rehearsal by someone else.
- [ ] **16.6 A real email provider** — until now every email (tickets, support replies, email confirmation links) is written to the development outbox. Choose a provider (Brevo, Mailgun, Amazon SES or similar), set `AFRICINEMAS_SMTP_*` and `AFRICINEMAS_MAIL_FROM`, and set up the domain's SPF, DKIM and DMARC records so emails aren't marked as spam. — **T:** a ticket email, a support reply and a confirmation link arrive in a real inbox, not spam; a failed send is retried and shows on the jobs check (16.2).
- [ ] **16.7 A status page, and telling people** — `status.africinemas.co.ke` on separate hosting (Better Stack, Instatus or similar), so it stays up when we're down: the live checks of 16.1 for the three sites, M-Pesa and email, and our updates during an incident. Cinemas and customers can subscribe by email or SMS. When an incident starts, every cinema's owner gets an SMS, email or WhatsApp (what's wrong, what to do meanwhile: the door list, 17.2), and another when it's over. Linked from the main site, every storefront footer and the back office. — **T:** a failed check shows on the status page within two minutes; opening an incident notifies every cinema owner, and closing it says it's over; the page answers while the app is stopped.
- [ ] **16.8 Incident runbooks, on call, and learning from incidents** — a written runbook for each kind of incident (the site down, the database down, M-Pesa failing, email not sending, a data breach: the Data Protection Commissioner told within 72 hours, 15.0), who is on call each week and how they're reached, and a short write-up after every incident (what happened, why, what changes), shared with the cinemas affected. A restore and a failover are rehearsed every quarter. — **T:** each runbook is followed once on staging by someone who didn't write it; the on-call rota is in the console.

### Phase 17 — Ready for real cinemas: production, resilience and a pilot

Planned 2026-10-24, from the owner's question of what it takes to run this as a business, and from the reliability practice of AWS's Well-Architected reliability pillar (recover automatically, test recovery, scale out, automate changes, no single point of failure) and Google's SRE book (a reliability target, the four golden signals: latency, traffic, errors, saturation). **Jac does use a database:** PostgreSQL (embedded in development, provisioned by `jac scale deploy` in production), which holds every cinema, order and ticket and our claims; media are files. Production protects all three: the app, the database and the files. **The target:** 99.9% a month (about 43 minutes down at most), measured from outside (16.1). Phase 16 and this phase are done before the first real cinema sells.

**Applies to every sub-phase:** as Phase 13. Nothing here weakens a cinema's isolation (ADR-0008) or puts a customer's details in a log or alert.

- [ ] **17.1 Every transaction, in the back office** — a **Transactions** section for staff who read payments (`payments.read`: owners, finance and general managers, auditors): every money movement at the cinema, one row each, newest first: online M-Pesa, M-Pesa at the counter, cash at the counter, refunds, and (Phase 15) AfriCinemas' fee and the cinema's share. Each row shows when, how much, how it was paid, its status (pending, paid, failed, cancelled, refunded), the order's reference, M-Pesa's receipt number, who sold it at the counter, and the showtime and venue; failed and cancelled attempts are listed too, so a customer who says "I paid" can be checked. Filters by day, venue, method and status; totals for what's shown; export as CSV for the accountant. Staff with venue-scoped roles see their venues only. Read from the ledger (append-only, P7.1), never a separate copy. — **T:** every kind of payment and refund appears once with the right status; a venue-scoped manager sees only their venue; an usher or box office agent is refused; the totals match the sales report and the ledger; the CSV matches what's shown; e2e on phone and desktop.
- [ ] **17.2 The door list** — for each showtime, a printable **door list** (seat, ticket reference, ticket type and the booker's first name, nothing more), downloadable as a PDF from the back office from the afternoon before, and the day's in one file. If AfriCinemas is down at showtime, door staff tick tickets off the list, and the customer still has their ticket email with its QR code and reference. When the scanner works again, tickets ticked on paper can be marked as used in one go. — **T:** the list holds every paid ticket for the showtime and nothing else; only staff who can scan or sell at that venue get it; it prints on A4 and a phone; e2e: download, tick, mark as used.
- [ ] **17.2b The offline scanner** (owner, 2026-10-31: before the pilot) — the scanner keeps working when it can't reach AfriCinemas: an installable web app (PWA) keeps a copy of the venue's tickets on the device (hashed references, seats and types; no customer details), up to date every 30 seconds, checks codes against it while offline, and uploads the scans when it's back; double entries and people let in anyway are shown to managers afterwards. Spec: `docs/specs/offline-scanner.md` (owner decisions O1–O5 there). — **T:** with the server stopped, an installed scanner lets in valid tickets and refuses used, wrong-showtime and fake ones; after reconnecting, every offline scan is recorded once; e2e with the browser offline; tried on real phones in airplane mode.
- [ ] **17.3 Staging and production** — two environments, the same shape: **staging** (deployed first on every release, with test data) and **production**.
  - **App:** `jac scale deploy` on managed Kubernetes, at least two copies (`min_replicas = 2`) on machines in different zones, autoscaling (`cpu_request` set), health and readiness checks, rolling deploys with no downtime, and the per-IP rate limit at the entrance.
  - **Database:** a **managed PostgreSQL** with a hot standby, automatic failover and point-in-time recovery, which every app copy uses (`JAC_DB_URL`), not the single in-cluster Postgres; daily backups copied to another region (16.5).
  - **Files:** object storage (Jac's S3 support) with versioning and a copy in another region, not a folder on one machine.
  - **In front:** Cloudflare for DNS, HTTPS, DDoS protection and caching the app's static files; a fallback page from Cloudflare's cache if the app doesn't answer, with AfriCinemas' support line and the status page.
  - **Where:** a region near Kenya (a Nairobi local zone or a Kenyan cloud) if the price is right; hosting abroad is allowed under the Data Protection Act with safeguards, stated in the privacy policy, and the advocate confirms nothing must stay in Kenya.

  — **T:** killing one app copy, or failing the database over, loses no request that was answered and no committed write; a restore to a point in time works on staging; a deploy causes no failed requests; the fallback page shows when the app is stopped.
- [ ] **17.4 Releases, versions and secrets** — every release goes to staging, passes its checks (CI, a smoke test of booking and paying with the simulator), then to production, and can be rolled back in one command. Jac's version is pinned and upgraded on staging first (we've logged 56 Jac issues, JI-038 and JI-042 among them; the baseline-bun swap after upgrades, JI-002). Secrets (Daraja keys, the ticket-signing key, SMTP, the Anthropic key) live in the cloud's secret store, never in files or images, and are rotated on a schedule. Dependencies are updated monthly. — **T:** a release with a failing check never reaches production; a rollback restores the previous version; no secret is in the repository or an image.
- [ ] **17.5 Load and security** — a **load test** on staging: a premiere's opening (500 people holding and paying for seats of one showtime within minutes, ticket emails, the scanner at the door), with the four golden signals watched, and the hold and order paths' known concurrency issues (JI-038) checked under it, with 11.1c's faster holds if the premiere needs them and 11.1b's claim reconciliation job running. A **security review**, and a penetration test by an outside firm before launch: sign-in, the isolation between cinemas, uploads, payments and the callback, the platform console, the AI booking assistant. **Signing out everywhere** (owner, 2026-10-26; JI-059), unless Jac has fixed it by then: a session code of ours, made right after Jac's sign-in and kept as a claim under the account, sent with every request and checked before every endpoint, the isolation registry included; changing a password, **Sign out everywhere** on Your profile, and disabling a member all delete the account's codes, so every other device stops at once, even with a valid Jac token. — **T:** the premiere completes with no double-sold seat, no lost order and answers within the target; every finding rated high is fixed before launch; after a password change or Sign out everywhere, another device's next request is refused and it's sent to sign in, for staff and customers, on every endpoint (the registry checks that none is missed).
- [ ] **17.6 Customer and cinema support** — AfriCinemas' own support line (one WhatsApp number and an email) on the main site, the status page and the fallback page, beside each cinema's own contact (14.3a); support hours set, with someone answering them; replies to cinemas through Help (13.5) within an agreed time; a short help page for customers (my tickets didn't arrive, I paid but have no tickets, the site is down). — **T:** the support line shows on every page listed; the help page answers the four common questions.
- [ ] **17.7 The business case** (mostly outside the app) — a cost model, kept up to date: hosting (app servers, managed Postgres, storage, Cloudflare), monitoring and the status page, email and SMS, the AI's use per cinema (designs and chat, tracked per cinema in the console), legal and accounting, and people (support, on call). Against revenue: the fee (Phase 15) on the tickets and snacks sold. What KenyaBuzz and others charge cinemas, found out from cinemas, so our fee and what it includes (the cinema's own storefront and brand, the AI design, the box office, the scanner, the door list) compare well. The break-even point in tickets a month. — **T:** the console shows each cinema's AI cost per month; the model is reviewed before the pilot and after it.
- [ ] **17.8 A pilot with one or two cinemas** — it starts only when every "Pilot" row of `docs/failure-modes.md` is ✅ (owner, 2026-10-31); a month with one or two friendly cinemas selling for real (with 11.3's demo data for training and 11.4's README and docs done first), after 17.1 to 17.6 and Phases 15 and 16: their staff trained (setup, the box office, the scanner, the door list, Transactions), AfriCinemas' support staffed for every showtime, the target and the four golden signals watched daily, and what we learn written down before more cinemas join. — **T:** the pilot runs its month within the 99.9% target, every customer issue is answered, and the go/no-go for opening to more cinemas is decided with the owner.
